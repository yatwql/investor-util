## 1. 外部机制解剖（借什么）

TradingAgents-astock 的决策反思是**「单标的评级 → 次日同标的再跑时结算」**的两阶段延迟反馈：

| 阶段 | 时机 | 动作 | 零 LLM 成本 |
|---|---|---|---|
| **A 记录**（`store_decision`） | 每次分析结束 `finalize_graph_run` | 把 `最终评级` append 进记忆日志，标签 `[日期\|代码\|评级\|pending]`；幂等（同日期同代码已存则跳过） | 是 |
| **B 结算**（`_resolve_pending_entries`） | **同标的再次跑** 的 `prepare_graph_run` 开头 | 对该标的所有 pending 条目拉真实行情（`_fetch_returns`：固定 `holding_days=5` 日历日 +7 缓冲），算 `raw` 收益与对沪深300的 `alpha`，LLM 产出 2~4 句反思（`reflect_on_final_decision`），**批量原子写**回填 tag + REFLECTION 段 | 行情拉取是，反思一次 LLM |
| **回灌**（`get_past_context`） | 每次分析的 PM 提示词 | 取该标的最近 N 条已结算 + 跨标的教训注入 `- Lessons from prior decisions...` | 是 |

**结构要点（memory.py）**：append-only markdown，HTML 注释 `<!-- ENTRY_END -->` 做硬分隔符（LLM 散文不会产出），tag 行结构化解析，`_apply_rotation` 只淘汰已结算旧条目（pending 永不丢），临时文件 + `os.replace` 原子写防半写损坏。`update_with_outcome`/`batch_update_with_outcomes` 同逻辑、批量版单次读单次写。

**指标口径（performance.py，本项目可完整借鉴）**：
- **方向正确率 `direction_accuracy`** 是唯一衡量判断准不准的：看多要**跑赢**、看空要**跑输**才算对（用 alpha 判，alpha 缺失退回绝对收益）；**Hold 不计入**（无方向无所谓对错）。
- **`up_rate`/`outperform_rate` 只描述标的长不长，与判断对错无关**——给出 Sell 后股价下跌是判断正确但 up_rate 记 0。曾因把 direction_accuracy 叫"胜率"导致 Sell 正确被记失败（v0.5.2 教训）。
- **样本门槛**：`MIN_MEANINGFUL_SAMPLE=20`，样本不足时明说"比率是噪音"，不据此判断流程有效与否。方向样本与总数样本的显著性判据**各算各的**（Hold 不计入方向，拿已结算总数做方向分母会高估）。
- 明确**不是回测**：持有窗口重叠、无仓位管理、无交易成本、样本选择偏差，不做夏普/年化。
- `rating_monotonicity`：五档 Buy→Sell 的平均 alpha 应单调递减，只在每档都有样本时判定（这是"这套流程准不准"最直接检验）。

**明确不借的部分**：结算由下次**同标的**运行触发、且历史行情经 yfinance 抓取——我方无"同标的每日单独分析"触发形态，也不宜引入 yfinance。

## 2. 我方现状盘点（落到哪）

### 2.1 我方产品形态 vs 外部
我方是**组合级、多模块、一次性复盘**：读持仓 Excel → 生成含行情/穿透/基金业绩/新闻关联 + LLM（智囊团/体检/穿透/全球宏观 + 辩论）的报告。**没有"每次对单只标的做评级"的载体**——评级/观点散落各 LLM 模块，无结构化字段、无按代码粒度的明确方向表述、无跨期积累。

### 2.2 可结算预测载体盘点（能否借鉴的关键）

| 载体模块 | 方向表达 | 按代码粒度 | 结算可行性 |
|---|---|---|---|
| **智囊团深度复盘 `expert_review`**（含辩论 pro/con/综合） | 「### 操作建议」表逐品种 `减仓/加仓/持有` + 置信度`高/中/低`；「### 情景分析」上涨/下跌 ±20% 逐品种行动（prompts_action.py:270-278, 300-333） | **是**（限直接持仓代码） | **最强候选**：方向词明确、可逐代码结算；但仅存于 HTML 文本，原始 Markdown 被丢弃、表格被 markdown 转换器降级为 `<p>` 纯文本（markdown.py:33-102 不支持管道表格），事后无法精确反推"哪个代码什么操作" |
| 持仓体检 `health_check` | 组合级五维度 `XX/100` + 评级`优/良/中/差`（prompts_core.py:91-114） | 否（组合/维度级） | 是"状态分"非"未来方向"，不直接对价格结算；可做"评分漂移"复盘而非胜率 |
| 穿透深度 `penetration_deep` | 集中度/外汇风险判断 + 建议 | 弱 | 静态结构风险，非价格方向 |
| 全球宏观 `global_macro` | 宏观叙事"对持仓潜在影响" | 否 | 无代码无方向，结算意义弱 |
| 新闻关联 `news_correlation` | 逐条新闻 `利好/利空/中性`（relevance+ sentiment JSON，唯一结构化输出） | 间接（事件→代码词法映射） | 方向附在新闻事件上非"某代码 N 日后涨跌"，结算口径另需设计 |

### 2.3 现有持久化/缓存（为什么不能直接复用）
- **LLM 缓存**（`data/cache/`，key=`llm_{module_key}_{fingerprint}`，fingerprint 仅含市值/成本/盈亏/持仓代码，**不含日期与观点**）：TTL expert_review 2h / 其余 1d / news 1h，**过期即删**。旧观点最多存一天，无法当观点库。
- **组合市值快照**（`data/history/snapshots/snapshot_{ts}.json`）：唯一跨期累积存储，保留 60 天/365 份。**`SnapshotData.llm_summary` 字段已预留但从未写入**（schemas/history.py:66,76；capture_snapshot 不填，_snapshot.py:67-73）——这是现成、为"快照级 LLM 摘要"预留的落点。
- **历史行情源已具备**：`history_stock_`（日线）/ `history_index_`（指数日线）数据模块（registry.py:226,228），TTL 周/月——结算所需的 N 日收益数据源已在系统内，无需 yfinance。
- 报告**只针对当前日期生成**（orchestrator.py 用 `datetime.now`），无历史日期复盘概念。

### 2.4 fact_checker 边界
只校验**生成当下可核验的**数值/品种/排名，对"看好/减仓"等观点词零校验；对情景/假设类主动跳过（_numerical.py 的 `_is_hypothetical_context`）。方向性预测天然无法当下核验——这正是跨期反思要补的维度，与 fact_checker 正交、不冲突。

## 3. 借鉴映射：落地方案（拟）

### 3.1 核心取舍：改"载体"而非照搬
外部以"单标的评级→结算"为单元，我方无此单元。**不能为反思新建单标的评级流程**（改产品形态、成本高）。改法：**把我方本就产出、本就逐代码、本就随行情日更的智囊团「操作建议」升级为可结算的方向记录**。

### 3.2 方案 A（推荐）：决策登记 + 快照侧结算 + 教训回灌
在保留现有 HTML 报告不变的前提下，**生成当下额外落一份结构化的「决策登记」**，供日后结算：

1. **登记（Phase A）**：`expert_review`/`debate` 的「操作建议」表在生成时**同步抽取**为结构化记录：`{复盘日期, 代码, 方向(减仓/加仓/持有→+1/0/-1), 置信度(高/中/低), 生成时组合指纹}`。抽取在 `_fetch_llm_and_news`/`generate_all_llm` 拿到 LLM HTML 之后做（需保留原始 Markdown 或在生成器内先解析再转 HTML）。追加写入按日期索引的决策登记文件。
   - 因操作建议限直接持仓代码且逐代码给方向 → 天然满足结算粒度。
   - 持有/中性（方向 0）不参与方向正确率，但保留用于评级区分度统计。
2. **结算（Phase B）**：**下次报告生成（任意日期）开头**，对过往 N 日前的未结算记录：用 `history_stock_`/`history_index_` 拉该代码自复盘日起的行情，算 N 日 `raw` 收益与对 `history_index_`（沪深300或合适基准）的 `alpha`。一次 LLM 反思调用，写回 2~4 句教训。历史行情不足（停牌/退市/过近）则保持 pending 下次再试。
   - **持有窗口口径**：我方是"减仓/加仓"动作而非"买入持有"，语义更接近"若按建议动作执行后的相对表现"，需设计（见 §5 口径）。初版可先按固定 `N 交易日`（如 5/20）算"该代码相对基准的 N 日超额"，再据方向判对错。
3. **回灌（教训注入）**：下次报告生成的 expert_review/debate/health_check 提示词注入 `决策历史` 段（同代码已结算 + 跨代码最近教训，限条数/截断防上下文膨胀），格式收敛为单行 tag + 2~4 句反思。

### 3.3 方案 B（最小侵入）：仅决策登记 + 统计快照，暂不回灌
只做 1+2（登记与结算/统计），把教训作为**报告内「历史决策复盘」区块**（数据快照式）展示，不注入后续 LLM 提示词。成本最低、无缓存耦合风险，先验证"这套分析准不准"。

### 3.4 方案 C（组合态复用现有壳）：写满 `llm_summary` + 快照侧趋势
不逐代码结算，而是把每次 expert_review 摘要写入 `SnapshotData.llm_summary`（填补现有空壳），跨期聚合出"观点漂移/评级演变"。优点：与组合演进视图天然同源、零新存储；缺点：非价格方向，无法算方向正确率。**适合作为 A/B 之上的轻量补充，不建议独立立项。**

> **推荐**：以 **B 起步**（最快验证分析有效性，风险最低），验证有效后再加回灌升级为 A；C 作为附带增强，与 A 落地的快照可复用 `history_snapshot` 基建。

## 4. 缓存与注入耦合风险（必须解决）

- **风险**：教训注入会改变 user_prompt/system_prompt 内容，但缓存键 `llm_{module_key}_{fingerprint}` 仅由持仓+行情快照决定，**不含教训内容**。直接注入会让注入前后的内容**命中同一缓存键**→ 陈旧缓存吞掉注入（或需 force 清缓存导致每次重算）。
- **对策**：注入 lessons 时，将 lessons 的稳定哈希并入指纹计算（新增一个 `fingerprint_extra` 概念，或把 lessons 拼进 fingerprint_fn 返回值）；或对注入教训的报告走 `force`/独立 cache 前缀。**设计阶段必须定夺**，否则回灌形同虚设。
- **教训内容自身去抖**：同一代码的教训应只在「有新结算」时变化，否则教训不变也会因注入改变指纹→缓存抖动。应让指纹只反映「教训集合的版本/最新结算条数」，而非每次追加都变。

## 5. 结算口径设计（对齐外部"命名即口径"纪律）

外部反复强调**指标命名即口径、误判会静默污染统计**。我方若做方向正确率，必须先用明确口径：

| 概念 | 外部口径 | 我方映射 | 争议点 |
|---|---|---|---|
| 方向正确 | 看多(买/加)→跑赢算对；看空(减/卖)→跑输算对；中性(持)不计 | 加仓(方向+)→N日跑赢算对；减仓(方向−)→N日跑输算对；持有不计 | **减仓的"收益"该用谁的**：减仓后个股若大涨，按"该代码 N 日收益 × 方向"会判错——但减仓的本意是降低风险敞口，组合层面的正确性无法用单代码收益衡量。需限定为"单代码方向判断的自我一致性"，明确声明局限 |
| alpha 基准 | 沪深300 | 持仓多为基金/ETF/股票混合，基准难统一。初版可用对应指数（股票→沪深300、ETF→其指数）或全用沪深300并注明局限 | 基金无法直接结算（净值 T+1、含申赎费）→ 初版**只结算股票与场内 ETF**，场外基金跳过 |
| 持有期 | 固定 5 日历日+7 缓冲 | 固定 N **交易日**（取历史日线序列第 N 根，天然跳过休市） | 与外部"行动建议→持有"语义需对齐 |
| 回看窗口 | 触发时点越久远越准 | 复盘日距今 < N 交易日的记录保持 pending | — |
| 样本门槛 | 20 条才给结论 | 沿用 20（组合级需很久才够，按标的/按方向展示时同样要门槛） | — |

**报告内呈现须含与外部相同的免责**："这是分析流程自身一致性的观察，不是回测/策略业绩/投资建议。"

## 6. 落地范围与成本（粗估）

| 环节 | 涉及 | 量级 |
|---|---|---|
| 决策登记抽取 | 生成器取原始 markdown → 解析「操作建议」表；新增登记文件读写 | 中（markdown 表降级问题需在生成器内先解析，或另设结构化决策输出） |
| 结算引擎 | 历史日线拉取 + raw/alpha 计算 + 一次反思 LLM 调用 + pending 管理 | 中（数据源已有 `history_stock_`） |
| 教训回灌 | 提示词注入 + **指纹并入教训哈希**（关键） | 小~中（指纹机制是最大改动点） |
| 统计/呈现 | 报告新章节 or CLI 子命令（借鉴外部 `tradingagents performance`） | 小 |

每项 LLM 反思调用成本低（短 prompt、低 max_tokens、可走 quick 档）。`direction_accuracy`/`MIN_MEANINGFUL_SAMPLE`/`rating_monotonicity` 等统计逻辑可**近直译**外部 performance.py（Apache 2.0，移植需保留许可声明并确认无传染依赖）。

## 7. 风险与不做清单

- **不建"单标的每日评级"流程**——改产品形态、成本高、与组合复盘定位冲突。
- **不引入 yfinance** 结算——我方已有历史日线模块。
- **不做回测/不年化/不算夏普**——遵循外部教训（重叠窗口+无仓位+无成本=伪精确）。
- **动作建议的方向判据不等于组合损益**——单代码方向一致性 ≠ 组合做减仓就赚了；报告必须明示局限，避免用户误读为"建议让我赚/亏了多少"。
- **避免教训污染当下分析**（陈旧教训=偏见）：注入的教训必须带日期+行情标签，提示词明确"以当下数据为准，历史仅参考"。
- **快照/cache 隔离纪律**：新增持久化决策登记文件须纳入 conftest `_isolate_sensitive_paths` 重定向；输出目录/缓存隔离与现有管线测试一致。

## 8. 结论

外部 TradingAgents-astock 的跨期反思机制对我方最有价值的部分**不是"单标的评级"外壳，而是三条可迁移内核**：
1. **两阶段延迟反馈**：判断当次不即时评判，真实行情落地后回看——避免"用今天的结果骂昨天的判断"。
2. **命名即口径的方向正确率 + 样本门槛 + 单调性检验**：判断流程准不准的可度量框架。
3. **教训以紧凑格式回灌进后续分析**，让模型看见自己过去的对错。

落地方案以**方案 B（决策登记+结算统计，暂不回灌）**为推荐起步，验证分析有效性后升级为 A（回灌教训）；同时填补 `SnapshotData.llm_summary` 空壳做组合态趋势补充。最大实现风险是**缓存键与教训注入的耦合**，必须在设计期解决指纹并入。
