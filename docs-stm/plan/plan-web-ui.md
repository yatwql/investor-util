## 1. 轻量 Web UI

### 概述

当前交互入口是 TUI（终端菜单）和 CLI（命令行参数），新用户门槛高。增加一个轻量 Web UI，通过浏览器即可上传持仓、触发报告生成、预览和下载结果。

### 收益

- **零学习成本**：不需要知道任何命令，打开浏览器上传 Excel 即可
- **分享简单**：生成的报告直接可以给 URL 让别人看（局域网内）
- **后台排队**：Web 模式下报告生成异步后台跑，不阻塞浏览器
- **复用现有管线**：`orchestrator.py` 编排层已完整，Web UI 只需调用它

### 风险

- 增加了攻击面：文件上传需做安全校验（恶意 xlsx、路径穿越）
- 用户可能期望 Web UI 替代 TUI 全部功能（配置修改、LLM 管理等），初始版不应覆盖所有
- 需要管理 Web 服务生命周期（启动/停止/端口冲突）
- 单人工具，Web UI 的"服务化"带来运维复杂度

### 工作量估算

| 阶段 | 内容 | 天数 |
|------|------|------|
| MVP 核心 | Flask/FastAPI + 上传页面 + 触发管线 + 结果预览/下载 | 3 |
| 功能补齐 | 配置页面（基本设置）、生成进度轮询 | 1.5 |
| 体验打磨 | 前端样式、错误处理、Loading 状态 | 1 |
| **合计** | | **5-6 天** |

### 建议策略

**MVP 不做：**
- 多用户（单人工具）
- LLM 配置在线修改（config.json 手动改更安全）
- 实时日志流

**MVP 做：**
- 上传 -> 选择输出格式(Excel/HTML/Both) -> 生成 -> 预览 -> 下载
- 从配置文件读取默认参数（如 LLM 开关、报告格式）
- 简单的生成进度展示（"步骤 3/12：正在获取行情"）

## 2. 首次运行引导

### 概述

当前首次运行直接报错"找不到 config.json"或"LLM 配置未设置"，对新手极不友好。添加首次运行检测 -> 引导流程。

### 收益

- **Hooked 体验**：用户第一次运行就看到交互提示而不是报错，留存量+50%（显然）
- **降低问问题**：不需要看文档就能完成首次配置
- **实现简单**：一个 `startup_wizard.py` 模块，检测文件存在性 -> 逐项引导
- **性价比极高**：~1 天工作量换来所有新用户的流畅体验

### 风险

- TUI 引导流程在 CI/定时任务模式会阻塞（需检测 `--non-interactive` 跳过）
- 依赖外部终端库（如 colorama）的交互占位，在纯 CLI 下需要备用方案

### 工作量估算：**1 天**

### 实现思路

```
首次运行检测
├── config.json 不存在 → 交互式创建（复制默认模板）
├── llm_key.json 不存在 → 提示跳过/输入 Key
├── holdings/ 为空 → 提示放置持仓文件 / 下载示例
├── LLM 设置为 claude 但无 key → 降级提示
└── 全部就绪 → 打印 "一切就绪，开始生成报告！"
```

## 3. 日志可视化

### 概述

当前日志是 `logs/app.log` 纯文本文件，异常排查需要翻数万行。增加一个 `--view-logs` 命令或 Web UI 中的日志 tab，以结构化的方式展示日志。

### 收益

- **异常追查快**：按级别(ERROR/WARNING/INFO)筛选、按时间范围过滤
- **数据源健康可见**：一眼看到哪些数据源近期频繁失败
- **复用日志系统**：已有 logging 的格式标准（`时间 [LEVEL] [module] message`），只需解析展示

### 风险

- 日志文件过大时（>100MB）解析会卡顿，需要 `tail -n 5000` 限制
- Web UI 模式下日志自动刷新可能导致高 IO（需手动刷新机制）

### 工作量估算：**1 天**

### 实现思路

两种入口：
- **TUI 模式**：`python tui.py --view-logs` → 终端内折叠式日志查看（类似 `journalctl -n 50 -f`）
- **数据源矩阵**：在报告末尾加一页"本次运行数据源状态"表，绿色=成功/黄色=降级/红色=失败

## 4. 错误友好提示

> **状态：✅ 已完成**（2026-07-27）
> - 核心实现：`src/python/report/data_source_matrix.py`（从 DegradationTracker 聚合各数据源状态）
> - 状态追踪：`src/python/report/data_status.py`（DegradationTracker 单例）
> - 渲染输出：报告章节 #17 数据源可用性矩阵（Excel + HTML 双格式）

### 概述

当前 akshare 连接断开时只记录 WARNING 日志，用户跑完报告不知道哪些数据是降级的。在报告输出页面加**数据源可用性矩阵**。

### 收益

- **信任报告**：用户看到所有数据源都是绿色，才对报告数据产生信任
- **诊断问题**：红色标记的数据源告诉用户"这个数据有问题，报告里对应内容可能不完整"
- **开发效率**：测试时一眼看到哪个源挂了，不需要翻日志

### 风险

- 矩阵列太多显得杂乱（当前 ~15 个数据源端点）
- 部分数据源是懒惰加载的，没被触发的不应标记为红色

### 工作量估算：**1 天**

### 实现思路

在 `orchestrator.py` 中注入一个全局 `DataSourceStatus` 上下文：
```python
class DataSourceStatus:
    sources: dict[str, Literal['pending','success','degraded','failed']]
```
每次 fetch 后更新状态，报告生成时读取渲染。

## 5. HTML 暗色模式

### 概述

为 HTML 报告增加暗色模式切换按钮，通过 CSS 变量 + 少量 JS 实现。

### 收益

- **晚间护眼**：晚上看报告不刺眼
- **极低成本**：纯 CSS 变量 + 一个 localStorage 开关
- **专业感**：暗色模式在金融工具中很常见，缺失显得过时

### 风险

- 部分已有 CSS 样式可能需要微调（如 Canvas 图表背景色）
- 打印时需要强制亮色模式

### 工作量估算：**0.5 天**

### 实现思路

```css
:root { --bg: #fff; --text: #333; }
[data-theme="dark"] { --bg: #1a1a2e; --text: #e0e0e0; }
```
JS：`<button onclick="toggleTheme()">🌙</button>` + `localStorage` 持久化。
