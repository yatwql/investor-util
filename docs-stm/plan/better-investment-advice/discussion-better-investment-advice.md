# 产品思考：从"数据呈现"到"切实投资建议"的鸿沟与路径

> **状态**：Tier 0 / MVP / Phase 1（20 项）/ Phase 2（19 项）/ Phase 3（P3-01~P3-13 + P3-17）已交付，P3-15 已取消，合计 73 项任务完成  
> **日期**：2026-07-20  
> **场景**：当前产品已有报表数据 + LLM 大模型提示语，如何让投资建议更"切实可执行"

---

## 1. 当前产品的"盲区"诊断

### 1.1 现状摘要

当前产品做的事：
```
持仓文件 → 行情数据 → 事实报表（Excel/HTML）+ LLM 解读（宏观/专家会诊/健康检查/穿透深研）
```

看似信息丰富，但仔细分析会发现**四大断裂**：

| 断裂 | 表现 | 后果 |
|------|------|------|
| **量化↔语义断裂** | 波动率、最大回撤、基准对比已算出但未传给 LLM | LLM 在不知道风险数据的情况下做"健康检查" |
| **事实↔归因断裂** | 知道各持仓盈亏，但不知道"谁在驱动风险和收益" | LLM 只能说"某股票涨了"，无法说"3 只重仓股贡献了 80% 波动" |
| **静态↔动态断裂** | 报告是时间点的快照，没有持仓行为建议 | 看完报告知道"账户怎样"，不知道"该做什么" |
| **通用↔个性断裂** | 所有投资者的报告结构和提示语相同 | 无法适配用户的风险偏好、持有期、税负情况 |

### 1.2 当前已计算但未有效利用的数据

有几个信号完全被浪费了：

| 已计算的数据 | 目前在 | 应该流向 |
|-------------|--------|---------|
| 年化波动率 | History sheet | LLM 所有 4 个模块 |
| 最大回撤 % | Drawdown sheet | expert_review, health_check |
| 基准对比（沪深300/标普500） | History sheet（图表） | LLM + Summary |
| 数据质量警告（收盘异常/断点） | logs + History sheet | health_check |
| 分红历史 | 已注册但**未接入生成管线** | fund_performance + LLM |
| F1 期间变动明细 | expert_review + health_check | rebalancing 模块 |

## 2. 改进方向：6 个层次

### 第 1 层：补全已有数据的信号（无新增外部数据源，但夏普需要 Phase 1 的 Rf 管线前置，纯算法）

**工作量低，价值高，最快见效。**

| 新增指标 | 计算方式 | 注入哪里 | 给用户的价值 |
|----------|---------|---------|-------------|
| **组合 Beta** | 持仓收益率 ~ 基准指数收益率 线性回归 | LLM 健康检查 + History | "你的组合波动比市场大 1.2 倍" |
| **夏普比率** | (年化收益率 - 无风险利率) / 年化波动率 | LLM 专家会诊 + Summary | "每承受 1 单位风险换来多少回报" |
| **卡玛比率** | 年化收益率 / 最大回撤 | LLM 健康检查 | "回撤控制效率" |
| **持仓收益贡献** | profit / total_profit | LLM + Summary sheet | "哪几只股票贡献了 90% 收益" |
| **持仓风险贡献** | weight × volatility / sum(all) | LLM + 风险归因 sheet | "哪只股票是最大风险源" |
| **集中度指数 HHI** | Σ(weight_i)² | LLM + Category | "组合到底有多分散" |
| **持仓胜率** | 盈利持仓数 / 总持仓数 | Summary + LLM | "你的命中率" |
| **换手率** | 期间变动金额 / 期间均值总市值 | LLM + Portfolio History | "交易频率评估" |

**代码改动量预测**：
- 新增 `src/python/analysis/metrics.py`（约 500-700 行，含截断保护、置信区间、边界处理）
- 修改 `registry.py` 注册 1–2 个新数据模块
- 重写 LLM prompt 结构——插入指标表 + 数据质量段落 + 信号置信度 + 行动模板，合计约 20h（P2-14 至 P2-17 为硬串行依赖链）
- 修改 `orchestrator.py` 在 `prepare_report_data()` 中调用新计算
- Beta 复杂度等级：**高**——需协方差计算、日期对齐、置信区间（估时约 40h/5天），拆分为 P2-11a（点估计，2天）和 P2-11b（置信区间+统计检验，3天，移至 Phase 4 与敏感性分析合并）

### 第 2 层：量化归因——"谁在驱动我的账户"

**核心算法**：
```
收益归因： 各品种收益贡献 = profit_i / Σprofit_j
风险归因： 各品种风险贡献 = w_i * σ_i / Σ(w_j * σ_j)     (简单版)
概念板块： 穿透后概念板块市值占比（已有数据，无需新数据源）
超额收益： 组合收益率 - 基准收益率 = Rp - Rb              (数据已有)
```
> **注意**：行业归因（Brinson 分解）因 3/4 关键数据源不可突破已放弃。替代方案：概念板块附加分析（利用已缓存的 `industry.concepts` 数据）+ 组合级超额收益。注意：替代方案不做归因分解——概念板块分析回答的是「你投了什么板块」而非「超额收益从哪来」。prompt 中删除「超额收益主要来自选股」类指引，改为「穿透板块分布如下，请据此分析集中度风险」。

**给用户的价值**：
- "你的账户收益中，60% 来自 A 股白酒板块，20% 来自港股科技，15% 是现金管理"
- "穿透后前 3 大概念板块（白酒、银行、医药）占持仓过半，集中度偏高"
- "穿透板块分布如下，请据此分析集中度风险"

### 第 3 层：执行信号——"该做什么"

这才是"切实投资建议"的核心。从报表到行动的跨越：

#### 3A 再平衡信号

| 信号 | 计算 | 触发条件 | 输出建议 |
|------|------|---------|---------|
| 单品种超阈值 | 单个持仓市值 / 总市值 > 15%（可配置） | 触发 | "XX 持仓占比 23%，建议部分止盈至 10–15%" |
| 权益/固收偏离 | 权益类占比 vs 目标比例（可配置） | 偏离 > 5% | "权益仓位从 70% 升至 78%，接近牛市高点特征，建议回调至 70%" |

#### 3B 风险预警

| 信号 | 计算 | 说明 |
|------|------|------|
| 持仓回撤历史分位 | 单品种当前回撤 vs 过去 1年/3年 分位 | "XX 处于近 3 年最大回撤的 85% 分位，接近历史极限" |
| 流动性风险 | 持仓市值 / 日均成交额 | "OTC 基金赎回上限 10 万/日，想全部赎回需 5 个工作日" |
| 汇率敞口 | 美元/港币持仓市值占比 | "约 30% 资产为美元计价，人民币近期升值影响约 -2%" |

#### 3C 情景模拟——"如果…会怎样"

**当前缺失但完全有能力计算的**：
- "如果今天卖出品种 X，释放多少现金？实现多少盈亏？"
- "如果市场下跌 20%，组合总回撤预计多少？（用 β 模拟）"
- "如果每月定投 X 元到品种 Y，3 年后预期分布？（蒙特卡洛）"

### 第 4 层：个性化适配——"千人千面的建议"

当前问题的核心之一：LLM 提示语对所有人一样。

**改进方案**：

```
用户画像输入（可配置项）：
├ 风险承受能力：保守 / 稳健 / 进取 / 激进
├ 投资期限：短期 (<1年) / 中期 (1-3年) / 长期 (3年+)
├ 投资目标：增值 / 收息 / 灵活
├ 每月现金流：可定投金额
├ 税务身份：中国居民 / 其他（影响分红税/H股红利税）
└ 经验水平：新手 / 有经验 / 专业
```

**影响**：
- LLM 提示语插入用户画像段落："根据您的持仓行为推断，您的风格倾向于{风险级别}（置信度：{高/中/低}）。建议通过问卷确认。"
- 再平衡阈值根据风险等级调整：保守 10% 警戒 → 激进 25% 警戒；推断置信度为 low 时锁定为稳健预设（15%/5%）；非问卷用户（仅推断）阈值上限硬编码 15%，不可被画像覆盖
- 矛盾场景（推断识别为双重标签）下 LLM prompt 输出双重标签而非单一风险级别
- 建议语言风格差异：保守→稳健为主，激进→机会提示更多
- 推断准确率需离线验证：用模拟持仓+已知画像做校验，设定基线 <70% 则不上线自动模式

### 第 5 层：竞争语境——"你和别人比怎么样"

**同行比较**（无需他人数据，用公开指数代替）：

| 指标 | 你的组合 | 沪深300 | 偏股基金指数 |
|------|---------|---------|-------------|
| 年初至今收益 | +8.2% | +5.1% | +6.8% |
| 最大回撤 | -12% | -15% | -14% |
| 夏普比率 | 0.85 | 0.62 | 0.71 |

LLM 据此输出："你的组合在牛市中略跑赢指数，且回撤控制优于平均水平，偏防御型配置特征明显。"

### 第 6 层：增强 LLM 策略——从"解读数据"到"模拟辩论"

当前 LLM 调用模式：单一提示 → 单次回复。

**改进方向**：

```
当前模式：
  数据 → [提示语] → 一次 LLM 回复

改进模式 1 - 多人辩论：
  数据 → [白脸/黑脸 两份提示语]
    ├ 白脸：列举持有理由（财务数据、行业前景...）
    └ 黑脸：列举卖出理由（估值贵、行业拥挤、政策风险...）
  → 两轮观点 → LLM 综合 → "建议持有但设止损"

改进模式 2 - 条件推理：
  数据 → "如果市场上涨 20%，哪种策略最优？"
           "如果市场下跌 20%，哪种策略最优？"
  → 分情景建议 → 用户根据自己判断选择

改进模式 3 - 反问引导：
  数据 → "你的组合中 XX 股票占比 25%，是否认为它值得这么集中？"
  → 引发用户思考，而非单向输出
```

## 3. 数据源与代码可行性实测验证（立项前调研核心）

> **贯穿原则**：所有结论必须有代码行号和数据结构支撑。每一层的可行性取决于数据源的稳定性和可用性。

**代码实况验证结果**：基于对 `src/python/` 全部 60+ 源文件的逐行审查，共识别出 6 个改进层次的 **62 项数据源可行性缺口**（Critical 13 项、High 18 项、Medium 19 项、Low 10 项、确认不做 2 项）。

#### 缺口严重度分布

| 严重度 | 数量 | 涉及领域 |
|--------|------|---------|
| Critical | 13 | 数据源不存在(Rf/行业指数/基准行业权重)、管线隔离、提示词缺陷、归因方案缺陷、用户画像缺失、安全基线 |
| High | 18 | 数据粒度不足、无行动指令、再平衡体系缺失、回撤缺个股级、质量孤岛、测试缺失 |
| Medium | 19 | 精度/聚合缺失、汇率敞口、缓存雪崩、概念板块未利用、熔断器孤岛 |
| Low | 10 | 格式化、缓存预热、部分安全改善、API成本 |
| 确认不做 | 2 | 多轮辩论、Euler分解 |

#### 各交付批次的估时与感知度

| 批次 | 估时 | 用户感知 | 新数据源 | 核心依赖 |
|------|------|---------|---------|---------|
| **Tier 0** | 1.5 天 | ★☆☆ 无感 | 无 | ✅ 已完成 |
| **MVP** | 4.5 天 | ★★★★★ 最强 | **0** | ✅ 已完成 |
| **Phase 1** | 20.5 天 | ★★★ 管线基础 | 1个(Rf) | ✅ 已完成 |
| **Phase 2** | 17.5 天 | ★★★★ 高 | 0 | ✅ 已完成 |
| **Phase 3** | 25.75 天 | ★★★★★ 最强 | 0个（885005降级） | P3-01~P3-13 + P3-17 ✅，P3-15 ❌ 取消，P3-16 待办 |
| **Phase 4** | 22-26 天 | ★★★★ 积累 | 0 | P2 待办 |
| **Phase 5** | 13.5 天 | ★★★★ 按需 | 0 | 按需评估 |
| **Phase D** | 2 天 | ★★★ 可选 | 0 | 独立决策 |
| **全量总计** | **~109.5 天(+buffer ~126-131d)** | — | 最多2个 | — |

**核心结论**：全量路线共 **~109.5 天纯开发**（含 buffer 约 126-131 天），约 **22-27 周**（5-6 个月，2 人团队）。组织方式按用户可感知价值分批次交付——**MVP 仅 4.5 天**即可交付用户可见改进（零新数据源），**Phase 1+2 共 38 天**完成全部量化信号建设。Phase 4+5（质量+画像）合计估时修正为 35.5-39.5 天。关键修正：Rf fetcher 实测东方财富 API 已不可用（替代源 bond_zh_us_rate 已验证 50/50 100%），DegradationTracker 的 report/ 层已有 6 处 record() 调用（perf_rank/industry/profit_forecast/dividend/index_a/index_us）但 **fetcher 层 6 处降级点（price/fund/industry/index）仍然缺失 record()**——T0-01-A 需在 4 文件 6 处逐一注入。Phase 1 估时从 124h 修正为 164h（实际任务合计，原头部低估 32%）。不含约 20% 协调 buffer。
