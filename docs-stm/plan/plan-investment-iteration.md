# 投资功能优化 — 迭代实施计划（20 轮，每轮量化验收）

> 关联：设计 [`plan-investment-features.md`](./plan-investment-features.md)（功能设计 + 章节归并方案 §4）· 顶层章节机制 `report_section_order`
>
> **定位**：本文档是**实施计划**，把「章节归并方案」落地为 20 轮可量化验收的迭代。核心约束：**21 章总数锁死**，全部功能作为现有章节的子模块/子块/子列融入，不新增顶层章节。每轮有**量化验收标准**，达标才进入下一轮。
>
> 前置：`plan-investment-features.md` §4 已定章节归并对照表。本文档按 §5 实施次序拆分为 20 轮。

## 1. 迭代总览

**总目标**：21 章锁死，全部功能归并为章节内子模块，功能从「事后体检」扩展至「买入比较 + 决策行动 + 数据可信」，用户感知章节不膨胀、单章更充实。

**阶段地图（20 轮 / 7 阶段）**：

| 阶段 | 轮次 | 主题 | 承载章节 |
|:--|:--:|:--|:--|
| **A 数据质量地基** | 1~3 | 数据质量仪表盘 | 改造 20 章 |
| **B 决策中枢** | 4~7 | 调仓建议/交易纪律/收益归因 行动板块 | 改造 14 章 |
| **C 历史增强** | 8~10 | 危机区间标注/尾部风险/快照差异 历史与演进增强 | 改造 18/19 章 |
| **D 风格与选基** | 11~12 | 行业 Beta 暴露 + 候选基金比较 | 改造 10/5 章 |
| **E 成本流水** | 13~15 | 资金流水 + 资金加权收益 | 输入扩展 + 改造 1/2/3 章 |
| **F 估值与温度** | 16~17 | 估值分位 + 市场温度 | 改造 4/1 章 |
| **G 导航与收尾** | 18~20 | 分组标签 + 文档 + 全链回归 | 全报告 + 发布门禁 |

**迭代原则**：
1. **每轮独立可交付**：每轮结束产物可运行、可测试、可回滚；
2. **每轮有量化验收标准**：测试数 / 覆盖率 / 计算精度 / 行为断言 / 向后兼容，达标才进下一轮；
3. **子模块默认关**：所有新子模块 config 开关默认关闭，避免 21 章内容突然"变胖"；开启后章节标题不变；
4. **不破坏既有**：旧持仓文件格式、旧 config、既有章节输出**向后兼容**（回归测试保证）。

## 2. 通用验收标准（每轮强制，不逐轮重复列出）

以下标准**每轮必过**，轮 1~20 的"量化验收"是对此的**叠加**：

- **[门禁-P0]** `python scripts/test_runner.py --mode dev-verify` 全部通过（核心单元 + 基础场景）；`python scripts/check-code-traces.py --ci`、`python scripts/check-doc-traces.py --ci`、`python scripts/check-task-numbering.py --ci` 三脚本通过。
- **[测试规范]** 新增/修改测试用例**必须标注对应 pytest marker**（`unit_*` 子标记，新 marker 注册到 `conftest.py` 并同步维护文档）；LLM 相关测试一律 mock（禁真实调用）。
- **[隔离]** 遵守 `_isolate_sensitive_paths` / 单例重置 / output_dir 重定向 / 持久化文件路径隔离；新持久化文件须加入 fixture。
- **[覆盖率]** 涉及模块整体覆盖率 ≥80%；**新增/改造模块 ≥85%**。
- **[向后兼容]** 旧持仓文件（无流水页签）、旧 config 解析与改造前**完全一致**（回归断言）；既有 21 章输出不因新子模块开关默认关而改变。
- **[回填]** 每轮完成：`docs-stm/managements/changelog.md` 记一轮；自审问题入 `review-findings.md`（修复后即归档）。
- **[架构]** 不违反 C1~C20（尤其 C3 原子写、C8 日志统一、C11/C12/C13/C14 测试规范、C16 路径绝对化、C18 凭据隔离）；管线共享层 `report/orchestrator.py` 不因 Web 无关改动而破坏。

## 3. 二十轮迭代计划

- **量化验收标准**：
  - [ ] 新增单元测试 **≥8 个**（正常品种 / 净值缺失 / 退市码 / 格式错码 / 名称不匹配 / 空账户 / 多账户 / 边界），标注 `unit_*` marker，全部通过；

## 4. 验收与发布流程

**每轮验收流程**（RED→GREEN→门禁→回填）：
1. 写测试（RED）：先按该轮"量化验收标准"写测试，标注正确 marker；
2. 实现（GREEN）：最小实现通过测试；
3. 覆盖率核查：涉及模块 ≥80%，新增 ≥85%；
4. 门禁：dev-verify + 3 check 脚本；
5. 回填：changelog 记一轮 + review-findings 处理；
6. **验收签字**：该轮全部"量化验收标准"勾选完成才进入下一轮。

**若某轮验收不达标**：不进入下一轮；拆分为子迭代继续，直到该轮验收项全绿（迭代轮次可扩展，20 轮为基线）。

**发布门禁（P2）**：轮 20 达标后，按 CLAUDE.md 发布门禁执行——`verify,regression` + 3 check + 版本号一致 + 数据快照刷新 + 打 tag。
