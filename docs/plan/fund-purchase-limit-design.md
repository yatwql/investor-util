# 基金申购限购信息接入 — 设计方案

> 文档版本：0.12.2-dev
>
> 定位：设计 + 已实施（`docs/plan/` 中间设计文件）。2026-10-03 设计评审通过后按 §8 实施，迭代 1~3（数据链路 → 展示集成 → 文档登记）已于同日完成；迭代 4（合并/调仓联动，二期）待另立任务，完成后随完成态归档。
>
> 关联计划：`plan-72`
>
> 核心前提（用户确认）：① 数据口径取**天天基金单口径**；② **数据需要稳定才有意义**——稳定性是本设计的第一约束，凡引入不稳定数据的方案一律降级或不采纳。

## 1. 背景与目标

**用户诉求**：

1. 持仓界面显示基金**申购限购状态**，尤其是 QDII（当前大量 QDII 处于「限大额 / 暂停申购」状态）；
2. 辅助**合并分析**：目标基金限购时，「把分散的同类持仓合并成一只」无法通过申购达成，调仓建议应据此降级提示。

**迭代结构（详见 §8）**：本期 = 迭代 1~3（数据链路 → 展示集成 → 文档登记，逐迭代验收）；二期 = 迭代 4（合并/调仓联动，§6），完成后另立任务。

## 2. 数据可得性与渠道口径结论

### 2.1 主数据源：天天基金申购状态总表（已实测可用）

天天基金官方数据页（`fund.eastmoney.com/Fund_sgzt_bzdm.html`）背后的全量接口：

```
GET https://fund.eastmoney.com/Data/Fund_JJJZ_Data.aspx
    ?t=8&page=1,50000&js=reData&sort=fcode,asc
响应：var reData={datas:[[...],...], count:N}   # 非标准 JSON，需剥前缀后解析
```

实测（2026-10-03，本机直连）返回 **27,695 行场外基金**，字段与诉求完全对齐：

| 字段 | 含义 | 实测样本 |
|:-----|:-----|:---------|
| 申购状态 | `开放申购` / `限大额` / `暂停申购` | — |
| **日累计限定金额** | 单账户单日申购上限（元） | 嘉实美国成长股票人民币：**100 元/日**；华夏全球股票(QDII)：**10,000 元/日** |
| 赎回状态 + 下一开放日 | 暂停申购时给出下一开放日 | `2026-12-08` |
| 购买起点 / 手续费 | 顺带可得 | — |

**覆盖面**：QDII/海外股票类 738 只中 **445 只当前限大额或暂停申购**——持仓展示与合并分析的主场景恰是高密度覆盖区。

### 2.2 渠道口径边界（明确不做的部分）

同一基金在不同渠道限额可能不同（如代销 10 元 vs 直销 100 元）。分渠道数据的现实可得性：

| 渠道 | 可得性 | 结论 |
|:-----|:-------|:-----|
| 天天基金（本数据源） | 免费结构化接口，每日更新 | **采纳为主口径** |
| 招行「QDII额度通」/ 理财通「额度宝」 | 数据来自付费 iFinD，无公开接口 | 不做 |
| 第三方工具站（额度日报等） | 人工核对爬公告，无稳定 API、口径不一 | 不做 |
| 基金公司公告原文（巨潮，项目已有 provider） | 可爬但需逐只解析非结构化公告，格式不统一 | 二期再议（仅当单口径被证明不足） |

**决策（用户确认，2026-10-03）**：取天天基金单口径，展示层**显著标注**「天天基金渠道口径，实际以申购渠道为准」。

## 3. 稳定性评估（核心章节）

> 「数据需要稳定，才有意义」——本章给出实测证据、风险清单与对策；§3.4 的四层保障是设计的硬约束。

### 3.1 接口实测（2026-10-03，本机直连，只读 GET）

| 测试项 | 结果 |
|:-------|:-----|
| 裸请求（无 Referer / 无 UA） | HTTP **200**，1.86s —— 无强制请求头要求 |
| 全量抓取 `page=1,50000` | HTTP **200**，2.3s，**4.17 MB**，27,695 行 |
| 带 Referer 连发 3 次（间隔 1s） | 全部 200，1.4~1.9s，无限流迹象 |
| 不带 Referer 连发 2 次 | 全部 200，0.22~0.25s |
| 鉴权 | 无（免认证、免 token） |
| 更新频率 | 每日（天天基金官方数据页口径） |

### 3.2 生态与历史证据

- **akshare 官方封装** `fund_purchase_em()` 已存在多年并写入官方文档（本机 akshare 1.18.64 实测可用），接口属天天基金官方数据页后端，非灰色接口；
- **社区实测东财风控阈值**：每秒 >5 次 / 并发 ≥10 / 1 分钟 ≥200 才触发临时封 IP。本项目使用模式为**每日 1 次全量**，低于阈值 2 个数量级以上；
- **已知风险先例**：东财曾对高频股票接口（`stock_zh_a_spot_em` 等）加滑动验证；akshare issues 中有东财接口格式变更的破坏记录（`akfamily/akshare#6106`、`#6239`）。基金数据页历史上相对稳定，但**不能假定永不变**——这正是 §3.3/§3.4 存在的理由。

### 3.3 风险清单与对策矩阵（风险编号 R1~R6，与复盘轮次无关）

| # | 风险 | 概率 | 影响 | 对策 |
|:-:|:-----|:----:|:----:|:-----|
| R1 | 临时限流 / 封 IP | 低 | 中 | 每日 1 次全量 + 项目既有熔断；触发后走过期缓存（标注数据日期），不影响报告生成 |
| R2 | 响应格式变更（`reData` 结构破坏） | 中低 | 高 | 载荷准入校验（§3.4-3）不通过即视为失败 → 备链路 → 降级；展示层「限购信息暂不可用」而非报错 |
| R3 | akshare 封装变更/破坏 | 中 | 中 | **主链路直连端点，不依赖 akshare**；akshare 仅作备链路 |
| R4 | 数据质量缺陷（「限大额」但金额为 0/空） | **已实测存在**（美元份额居多） | 中 | 校验规则识别 → 展示「限额未知」，绝不显示 0 元误导 |
| R5 | 口径单一导致与实际申购渠道不符 | 已知边界 | 低 | 展示层固定脚注声明口径（§5.3） |
| R6 | 缓存过期后长时间不可用 | 低 | 低 | 过期缓存兜底 + `data_status` 追踪记录，人工可感知 |

### 3.4 稳定性保障设计（四层，硬约束）

1. **使用模式**：每日报告生成时抓取 1 次全量 → 缓存 TTL 1 天。非按需高频调用，天然远离风控阈值。
2. **双链路 Provider Chain**（复用 `fetcher/chain.py` 既有习语）：
   - 主链路：直连端点（`make_http_client`，Referer + UA，超时 15s，载荷轻量解析——剥 `var reData=` 前缀后 `json.loads`，不引 demjson）；
   - 备链路：`ak.fund_purchase_em()`（封装解析，应对主端点格式变更）；
   - 兜底：过期缓存 + `fetched_at` 时间戳随数据返回。
   - **冗余性质如实声明**：备链路与主链路共享同一上游端点，提供的是**解析器冗余**（直连解析器 vs akshare 封装，任一被格式变更击穿时另一条可能仍活）而非**源冗余**——端点整体不可用时两链同时失败，**真正的可用性兜底是最外层的过期缓存**。免费层不存在独立的分渠道替代源（§2.2），不虚构第三链路。
3. **载荷准入校验**（仿 `rank_payload_is_current` 语义版本习语，`cache_validate` 挂载）：
   - 可解析且行数 **≥ 20,000**（正常 2.7 万，骤降即异常）；
   - 载荷携带语义版本字段 **`purchase_schema`**（沿用 `rank_schema`/`hold_schema` 习语）——未来字段演进时抬版本号即可让旧缓存自动作废，不依赖 TTL 自然过期；
   - 必需字段齐全（`基金代码/申购状态/日累计限定金额` 等 12 列）；
   - **值域体检（防位置错位）**：响应行是无键数组（按位置解析），若上游插入列则字段全体错位但「字段齐全」仍会误过——必须校验：基金代码 100% 为 6 位数字、申购状态 ∈ 已知枚举（开放申购/限大额/暂停申购/…）、日累计限定金额可解析为非负数值；任一值域命中异常即判失败；
   - 持仓代码命中核对由 **fetcher 调用方**执行（`cache_validate` 只验载荷自身，不持有持仓上下文）；
   - 任一不满足 → 本次抓取判定失败，走降级，**旧缓存不被污染**；
   - **读取时同样执行**（含读过期缓存展示时）——校验挂在 `cache_validate` 上，损坏/截断的缓存体不得流入展示层。
4. **展示层时效与降级（陈旧阶梯，硬上限）**：数据带 `fetched_at`，时效按**交易日**计（时间距离以交易日计纪律）：**≤3 交易日**正常展示；**4~7 交易日**展示但标「数据陈旧」；**>7 交易日**一律显示「—」——**过时的限购信息比缺失更误导**（显示「开放」实际已限购会直接坑害合并决策），宁可缺不可错。完全不可用时限购列整体隐藏，**报告生成流程不受影响**（模块级隔离，符合 datasource-reliability §1 三级失败路径）。

## 4. 数据链路设计

### 4.1 语义命名（先定名再设计）

| 语义名 | 类型 | 职责 |
|:-------|:-----|:-----|
| `tiantian_purchase` | provider 模块 | 天天基金申购状态总表抓取与解析 |
| `fetch_fund_purchase_status` | fetcher 函数 | 双链路获取全量申购状态（chain + 校验 + 追踪） |
| `fund_purchase_status_` | 缓存键前缀 | 全量表单键缓存（非按代码分键），TTL 1 天 |
| `purchase_status_payload_is_valid` | 校验函数 | §3.4-3 载荷准入 |
| `PurchaseStatus` | 数据契约 | `{purchase_status, redemption_status, next_open_date, daily_limit, min_purchase, fetched_at, source}` |
| `fund_purchase_limit` | 功能开关 | 展示/链路总开关；入 features.json 注册表**报告组**（开关注册表单条声明，分组/默认值/显示名由注册表派生，默认开，三渠道入口同源），兼作数据源 kill-switch，**不建平行配置路径** |

命名纪律：不得用任务编号命名任何标识符。**实现落地时**再登记进技术设计文档「功能语义命名表」（该表与代码双向校验，未实现前不得提前登记）。

### 4.2 取数与缓存

- 单键全量缓存（一次抓取覆盖全部持仓代码），报告生成前置拉取一次，同会话内经 `DataSourceRegistry.session_cache` 复用（会话级 API 复用），不重复抓取；
- 缓存一律经 `cache/` 子包 `get()`/`set()`（缓存统一管理与原子写入），不直接操作 `data/cache/`；
- 重试/退避用 `core/retry.py` 策略参数（重试退避唯一原语），请求间隔用 `core/throttle.py`（间隔节流唯一原语），不自建 sleep/抖动算式；
- 成功/失败均接入 `data_status` tracker 与东财/天天基金熔断计数（`record_success/record_failure`）；
- 解析产物供持仓页与后续分析模块共用；状态经 pipeline 数据流传递，**不写入模块级全局变量**（渲染期数据不写模块级全局纪律）。

### 4.3 架构设计约束对照（逐条核验）

> 下表行名即技术设计文档「架构设计约束」表中的语义名（按文档纪律不引约束代号，回查请以语义名检索该表）。

| 约束（语义名） | 本设计的遵守方式 |
|:-----|:-----------------|
| 代码类型判定中心化 | QDII/场外基金识别复用 `core/code_utils.py` 判定函数（含「QDII 优先展示」标记），不自建前缀表 |
| 缓存统一管理与原子写入 | 全量表经 `cache/` 子包读写，前缀 `fund_purchase_status_` |
| 会话级 API 复用 | `DataSourceRegistry.session_cache`，报告一次生成内单次抓取 |
| HTTP 客户端统一 | 直连端点经 `core/http_client.make_http_client` 构造，不自建 requests |
| Provider Chain 必经 | 经 `fetch_with_fallback`，新链 `fund_purchase` 注册进 `fetcher/chain.py::_DEFAULT_CHAINS` |
| 渲染期数据不写模块级全局 | 展示数据经 pipeline 契约传递（见下行） |
| pipeline_data Schema 契约 | 以 `purchase_status_data` 契约注入（`available/reason/rows` 形状，与 `financial_indicator_data` 同形），报告层只读契约 |
| 功能开关注册表唯一事实来源 | `fund_purchase_limit` 在 features.json 注册表单条声明，默认值由注册表派生，三渠道入口同源 |
| 时间距离以交易日计 | 陈旧阈值 3 个交易日（§3.4-4、§5.4） |
| 重试退避/间隔节流唯一原语 | 分别复用 `core/retry.py` / `core/throttle.py` |
| 测试纪律（标记/边缘隔离/敏感隔离） | marker 注册、edge 用例入 `*_edge.py`、缓存/输出目录隔离（§7） |

> **Provider Chain 必经的连带义务**：新链注册后必须同步更新 `docs/manuals/datasource-reliability.md` §4.2 链路表——该表与 `chain.py::_DEFAULT_CHAINS` 逐链对应，由 `check-doc-drift.py` 第 15 项**双向断言**（漏链/幽灵链均报错）。

### 4.4 技术债防护 — 单源清单

凡下述逻辑出现**第二份实现**即为新增技术债，评审应拒收：

| 逻辑 | 唯一事实来源 | 反模式 |
|:-----|:------------|:-------|
| 陈旧阶梯判定（≤3 / 4~7 / >7 交易日） | 单一 helper，Excel/HTML 渲染层调用 | 两处各写一套阈值 |
| 0 元/缺失限额 → 「限额未知」 | 解析器内单点转换 | 展示层各自判空 |
| 口径脚注文案 | 单一常量/渲染函数 | 两处硬编码文案漂移 |
| 代码 → 状态查询 | `get_purchase_status(code)` 入口函数 | 渲染层直接碰 rows dict |
| 载荷格式演进 | `purchase_schema` 语义版本字段 | 格式变更后旧缓存残留靠手清 |

## 5. 持仓界面展示设计

### 5.1 展示位置与管线集成

**集成链路**（数据不落模块级全局，经 pipeline 契约传递）：

```
报告编排层数据构建阶段（pipeline_data_builder 同层）
  → fetch_fund_purchase_status()          # chain + 校验 + 缓存，会话内单次（C4）
  → pipeline_data 增 purchase_status_data  # {available, reason, rows, fetched_at} 契约
  → 渲染层只读契约：Excel 明细 sheet / HTML 持仓页
```

**展示位置**：

- **持仓明细表**（Excel sheet 与 HTML 持仓页）：基金行追加「申购状态」列——**沿用 `cost_lots` 条件列先例**：开关开启且数据 available 时追加子列，否则保持既有 15/16 列输出逐字节不变（不破坏既有列契约与「报告序号与显示名不可硬编码」纪律）；
- **QDII 优先**：非限购基金可只显示状态点，限购/暂停基金显示完整信息，避免列宽膨胀；QDII/场外识别走 `core/code_utils.py`（代码类型判定中心化）；
- **契约形状**：`purchase_status_data` 与 `financial_indicator_data` 同形（`available/reason/rows/failures`），`available=false` 时渲染层静默隐藏列（有 reason 可供排查），**不抛异常、不出占位噪音**。

**非目标（本期）**：不改 Web/TUI 独立持仓页面——用户所指「持仓界面」即报告产物（Excel + HTML）；若后续需要 Web 同源展示，直接读同一 `purchase_status_data` 契约，不新建第二条链路。

### 5.2 状态视觉语义

| 状态 | 标记 | 附加信息 |
|:-----|:----:|:---------|
| 开放申购 | 🟢 开放 | — |
| 限大额 | 🟡 限大额 | 「日限 X 元」；金额 0/缺失 → 「限额未知」（风险 R4） |
| 暂停申购 | 🔴 暂停 | 「X月X日开放」（来自下一开放日） |
| 数据不可用 | ⚪ — | 不显示猜测值 |

**查无此码**（场内份额、新基金未入库等）→ 显示「—」，**绝不默认「开放申购」**——危险猜测比缺失更有害；场内持仓本身无「申购」语义，同样归入「—」。

### 5.3 口径脚注（固定展示）

> 申购状态与日限额为**天天基金渠道口径**，每日更新；其他渠道（基金公司直销、银行等）限额可能不同，实际以下单渠道显示为准。

### 5.4 数据时效标注（陈旧阶梯）

| `fetched_at` 距今（交易日，按交易日历计） | 展示行为 |
|:-----|:-----|
| ≤ 3 | 正常展示状态与限额，附抓取日期 |
| 4 ~ 7 | 展示 + 「数据陈旧」黄标 |
| > 7 | 显示「—」（不展示可能过时的限购状态，宁缺毋错） |

**固有限制（登记）**：响应体不含数据自身日期字段（仅净值报告时间），时效以「抓取时间 + 交易日历」近似推算；周末/长假不计入陈旧（数据源本就不更新）。

## 6. 合并分析联动（二期，本期不实施）

1. **合并可行性判定**：whatif / 调仓建议中，目标基金为限大额或暂停时，「申购合并」路径降级为提示「当前限购，无法通过申购合并」；
2. **合并天数估算**：`需合并金额 ÷ 日限额`，超过合理阈值（如 60 个交易日）直接判定路径不可行，避免给出「需 28 年」式无意义建议；
3. **替代路径提示**：暂停申购时引用下一开放日；限购时提示可选替代标的或等待；
4. **范围边界**：仅影响建议文案与路径选择，不改动既有调仓算法的数值计算。

## 7. 测试计划

**载体纪律（硬要求）**：

- 新增用例一律标注既有 pytest marker（测试标记强制，就近选 `unit_providers` / `scenario_*`，新增 marker 须先注册进 `conftest.py`）；
- 异常样本用例（0 元限额、行数骤降、字段缺失）属 edge 场景，**必须入 `*_edge.py` 文件并标 `@pytest.mark.edge`**（边缘测试文件隔离，收集期自动校验）；
- HTTP 层不经真实网络：优先经 **传输工厂注入**（HTTP 客户端统一点上的 `use_transport_factory` 记录-回放）回放样本，次选 monkeypatch 调用点模块（网络守卫 `BaseException` 兜底，漏 mock 瞬时硬失败）；
- **禁止断言可演进总数**（check-test-redundancy 第 5 类）：不得写死「总行数 27,695」「QDII 限购 445 只」等当前统计值——只断言结构关系与校验规则本身。

**用例清单**：

| 层 | 用例（每条降级路径至少一条回归用例） |
|:---|:-----|
| 单元 | 解析器：裁剪真实响应样本 fixture（含 `var reData=` 前缀、限大额+正常金额、限大额+0 元、暂停+下一开放日四类代表行）→ 断言契约字段逐项正确 |
| 单元 | 准入校验：行数不足 / 字段缺失 / 不可解析 → 判定失败且**旧缓存不被污染**；合法载荷过校验 |
| 单元 | 降级阶梯：主链路失败 → 备链路 → 过期缓存（≤7 交易日带标 / >7 交易日隐藏）→「暂不可用」逐级断言 |
| 单元 | 陈旧阶梯：按交易日历构造 `fetched_at`，验证 ≤3 / 4~7 / >7 三档展示分支（含长假不计陈旧） |
| 单元 | 0 元限额 → 「限额未知」（风险 R4 回归用例）；口径脚注恒在 |
| 场景 | 管线集成：开关开（列渲染 + 契约注入）/ 开关关（15/16 列逐字节不变）双场景；`available=false` 时静默隐列 |

**隔离纪律**：全程遵守网络 mock 强制（`_block_external_network`）；管线场景测试将 `output_dir` 重定向临时目录、不依赖真实持仓（fixture 最小持仓 2~5 品种）；缓存目录由 conftest 自动重定向；本模块无 LLM 调用，不涉 LLM mock。

## 8. 迭代拆分与验收标准（评审通过后按序实施）

> 原则：每迭代**单一职责、独立可验、可单独回滚**；展示未上线前报告输出零变化；验收条目全部可判定（跑某命令/断言某输出），不用「正常」「应该」类措辞。

### 迭代 1 — 数据链路（无展示）

**交付物**：`providers/tiantian_purchase.py`（直连解析）+ `fetch_fund_purchase_status`（chain 接线 + `purchase_schema` 准入校验 + 缓存 + 熔断/`data_status`）+ `_DEFAULT_CHAINS` 注册 + reliability §4.2 表同步 + 解析/校验/降级单测。

**验收标准**：

1. 本地触发一次真实抓取：HTTP 200，解析行数 ≥ 20,000，载荷含 `purchase_schema` 版本字段（**实施期手工验证项，仅此一条出网；测试套件仍全程无网**）；
2. 单测通过：4 类代表行解析断言、校验失败不污染旧缓存、四级降级逐级断言；
3. `check-doc-drift.py --ci` 通过（`_DEFAULT_CHAINS` 与 reliability §4.2 表第 15 项双向断言）；
4. `check-test-redundancy.py --ci` 通过；用例带 marker，edge 用例在 `*_edge.py`；
5. **零展示影响证明**：本迭代不动报告层，既有管线场景测试输出与主干基线一致；
6. `ruff check` / `ruff format --check` 零告警。

### 迭代 2 — 展示集成

**交付物**：`purchase_status_data` 契约注入 pipeline + Excel 条件列（cost_lots 先例）+ HTML 持仓页 + 口径脚注/陈旧标 + 单源 helper（§4.4）+ `fund_purchase_limit` 开关入注册表报告组（开关注册表唯一事实来源）+ 展示层测试。

**验收标准**：

1. 开关开：持仓明细新增列渲染，限大额行显示「日限 X 元」、暂停行显示下一开放日；
2. **0 元限额显示「限额未知」**（回归用例，R4 风险）；
3. **开关关：明细表输出与主干基线逐字节一致**（15/16 列不变）；
4. `available=false` 时静默隐列且报告生成成功（管线冒烟）；
5. 陈旧阶梯三档分支单测通过（≤3 / 4~7 / >7 交易日，含长假不计）；
6. 口径脚注恒在（Excel 与 HTML 同源文案）；
7. 开关入注册表后 `check-doc-drift.py --ci` 开关项通过；
8. 管线场景测试输出目录重定向临时目录，`test-runner.py --mode dev-verify` 通过。

### 迭代 3 — 文档登记与收尾

**交付物**：`datasource.md` / `datasource-reliability.md` 新源详表节（含限流/降级/最后验证日期，按 §3 实测填写）+ `testplan.md` 用例登记 + `folders.md` 目录树/统计刷新 + 技术设计「功能语义命名表」登记 + 视粒度登记需求条目 + `changelog.md`。

**验收标准**：

1. P0 门禁十项全绿：`test-runner.py --mode dev-verify` + **9 个** `--ci` 脚本（code-traces / doc-traces / task-numbering / semantic-index / doc-drift / test-redundancy / requirement-trace / version-consistency / doc-links）全部退出 0；
2. 语义命名表登记后 `check-semantic-index.py --ci` 正反向通过；
3. 若登记需求条目：`check-requirement-trace.py --ci` 双向通过；
4. `collect-test-coverage.py` 重跑后 test-coverage.md 计数无漂移。

### 迭代 4（二期）— 合并/调仓联动

**前置**：迭代 2 完成（依赖 `purchase_status_data` 契约）；立项后在 plan.md 另立任务编号。

**交付物**：whatif/调仓建议的限购约束（§6）+ 合并天数估算 + 降级文案 + 三态测试。

**验收标准**：

1. 目标基金限大额/暂停时，合并/加仓建议输出降级提示（含日限额或下一开放日）；
2. `需合并金额 ÷ 日限额 > 60 交易日` → 判定路径不可行，不出无意义建议；
3. **零回归证明**：数据不可用时建议回退现网行为，调仓数值与主干一致（回归用例）；
4. 单测覆盖 开放/限购/暂停/无数据 四态；
5. P0 门禁全绿。

**依赖关系**：迭代 1 → 迭代 2 → 迭代 3（串行）；迭代 4 独立后置。Jev 线（评测/接入）与本线互不依赖，可并行推进。

**预估成本**：迭代 1~3 合计低（一个 provider + 一个 fetcher 函数 + 展示列 + 文档）；**风险**：低（四层降级保证对现有流程零破坏，迭代 2 验收第 3 条可机器证明零破坏）。
