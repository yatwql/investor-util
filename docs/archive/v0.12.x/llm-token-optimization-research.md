# LLM 调用链 token 消耗优化空间调研

> 日期：2026-10-06。**前提：不降低任何调用效果**——只评估调度/记账/缓存语义层手段；效果敏感项（prompt 内容削减、thinking 预算调低、模块裁剪）一律排除在候选之外。
> **结论：维持现状**。唯一行动项为计量正确性修复（[review-findings](../managements/review-findings.md) rf-596：把账算对，不改任何消耗与行为）。

## 1. 调用链现状

```
generate_all_llm（编排：指纹预检 → 可跳过模块直接走内容缓存，零调用）
   └─ generate_llm_module（骨架：按模块组装 prompt）
        ├─ system = 模块专属 system + 合规声明尾部追加（幂等）
        ├─ user   = 模块指令与正文数据 + 统一附录（共享数据块，挂尾）
        └─ call_llm（多 provider 链式尝试，首个成功即返回）
             └─ call_llm_with_retry（core.retry 统一退避）
                  └─ PacingGate（端点级 min_interval/jitter/max_concurrency 节流）
                       └─ _api_claude / _api_openai / _api_gemini
                            └─ _log_token_usage + track_session_usage（计量）
```

- 统一附录在 `skeleton._build_prompt_appendix` 拼装，随每个模块调用携带（跨模块一致性设计）。
- 每模块独立 system（`_SYSTEM_GLOBAL_MACRO` / `_SYSTEM_EXPERT_REVIEW` … 各不相同）。
- Claude 路径对 system 打 `cache_control: ephemeral`（`_api_claude`）。

## 2. 既有省 token 机制盘点（已做满的部分）

| 机制 | 位置 | 作用 |

## 5. 共享前缀前移专项评估

### 5.1 机制

提示词缓存按「从第 0 字节起逐字节相同的前缀」匹配（Anthropic 显式断点 / OpenAI 自动取最长公共前缀）。现状每次调用的字节流自第 0 字节起即分叉（模块专属 system + 模块专属正文），共享的统一附录挂在最尾部——**公共前缀长度 ≈ 0，三家缓存全部无法生效**（与 §3 大运行命中 0% 实测一致）。前移 = 把共享内容挪到请求开头：第 1 次调用写入（Anthropic 写入 1.25×、TTL 5 分钟、有最小长度门槛），后续调用读取（0.1×）；OpenAI 侧无需标记、自动按公共前缀命中。

### 5.2 收益

- 共享段 S ≈ 1.5k tokens 时：附录部分从 9×S 全价 ≈ 1.5S（首写）+ 8×0.1S ≈ 1.8S → **省 ≈ 输入侧 45%（≈11k tokens/轮）**。
- 折算费用：输入通常占单轮费用 20~40% → **总费用省约 10~25%**，仅对**按量计费**端点成立；主力 kimi 订阅/配额制下账单几乎无感。
- 输出侧（大头）一分钱不省；调用次数不变；重试时同前缀同样命中。
- **缓存命中本身绝不改效果**（命中与否，模型收到的字节完全相同）。

### 5.3 风险

1. **重排本身 = 未验证的 prompt 变更**：「指令在前、数据在后」变为「数据在前、指令在后」，注意力分布与指令遵循度会变化；温度>0 下无法低成本自证「不变差」，严格解释下与「不降低调用效果」硬前提冲突。
2. **工程连锁**：prompt 组装顺序变化 → 全模块指纹重算（内容缓存一次性失效）→ 注入/接线测试、关态回退哈希、指纹单测、prompt 结构文档同步；Anthropic 断点须拆 content block 且共享段低于最小长度门槛则完全不生效；写入溢价与 5 分钟 TTL 受 pacing（20s 串行 + 长思考调用）相邻间隔临界影响。
3. **边际收益小**：绝对量仅输入侧 25k/轮，订阅制下不产生可见费用。

### 5.4 判定与触发条件

**维持现状。** 满足以下任一条件时重启评估，且**不直接上**，先做影子 A/B（开关关态跑现状、开态跑前移，对照结构相似度 + 人工抽检）：

1. 输入侧规模膨胀（共享数据段每轮 >50k tokens，或模块数翻倍）；
2. 主力切回按量计费端点且缓存折扣在账单上可见。

## 6. provider 差异度（四层）

| 层 | 差异度 | 说明 |
|:--|:------:|:-----|
| 输入 token 总量 | ≈0 | 同一 prompt 同一文本，仅各家 tokenizer 口径差 ±10~20% |
| 输出 token 总量 | 中 | 模型差异 > provider 差异；thinking 记账（Anthropic 计入 output）、强制推理族 effort/budget 两套控制由登记表兜底 |
| 计量可见性 | **大** | `_normalize_usage_tokens` 归一：claude 读 `cache_read_input_tokens`；openai 读 `prompt_tokens_details.cached_tokens`（缺失回退 0）；Gemini 归一形无该字段恒 0——归一化前 OpenAI 系命中恒 0（rf-596） |
| 缓存机制 | **大** | Anthropic 显式断点/0.1×读/1.25×写/5min TTL/最小长度门槛；OpenAI 自动前缀缓存（无需标记）；Gemini 另一套——**「能省什么」是 provider-specific 的** |

跨 provider 恒成立的只有 §2 既有机制（跳过/去重/避免重发）；附录类共享内容吃缓存，三家都要求**共享前缀前移** → 归入 §5 判定。

## 7. pacing 维度（两条缝隙，收益≈0）

实配（kimi-code）：`min_interval=20s, jitter=0.2, max_concurrency=1`——单端点全串行、20 秒一发。

1. **pacing 不改单次调用量**：只节流，不碰 prompt。
2. **缝隙 A：缓存窗口**——Anthropic 命中要求相邻调用落在 5 分钟 TTL（滑动）内；20s 串行 + 长思考调用使轮内间隔偏大，是大运行命中 0% 的时间侧原因（结构侧原因为 system 各异、无共享前缀）。但当前结构下无共享前缀可命中 → 放宽 pacing 换命中的理论收益 ≈ 0。
3. **缝隙 B：重试率**——节流过紧 → 429 → 整包重发；429 通常未受理不计费，浪费有限；429 诊断已按端点给可执行建议。
4. **拉扯**：放宽 → 窗口内命中率升、429 风险升；收紧 → 反之。当前配置是订阅端点防风控的合理保守值，两条缝隙的可省额均 ≈ 0。

## 8. 结论

1. **调度/参数层面没有值得做的省 token 项**：唯一结构性候选（共享前缀前移）与「不降低调用效果」硬前提冲突，且收益集中于输入侧这一小头、订阅制下几乎无感 → **维持现状**。
2. **provider 差异不改变结论**：token 消耗量跨端点差异小（输入同文本、输出同模型），费用与读数差异大；可省项在三家的成立条件相同（都要动 prompt 顺序）。
3. **行动项只有计量正确性**：rf-596（非 claude 分支缓存命中读取）——零效果风险、零消耗变化，让 OpenAI 系端点已存在的缓存折扣可见。
